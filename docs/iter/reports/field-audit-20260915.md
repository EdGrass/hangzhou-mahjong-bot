## 4. 关于副露轴：既有一个测量错误，也有一个「不是杠杆」的实测结论

### 4.1 测量错误（事实成立）

`bot/speedtugc.py` 的设计依据写的是 E020：「顶级席副露 1.128 < 我方 1.241」。
本次独立复算：**我方 0.866，顶级 1.143**（同房配对 t=11.81，对手更高占 72%）。
→ **顶级副露比我方多**，E020 对我方的那个数是错的（顶级那个数复算吻合）。

### 4.2 但这个错误**没有造成损失**——门控不是杠杆（实测）

**Δ分/轮 = -0.167 ± 0.686（t = -0.48）→ 噪声内，无差异。** 副露被抬高 39%（正好到前排水平），
胜率与爆头纹丝不动。

`tools/offline_replay.py` 在**真实窗口**上回放同一改动（碰/吃窗口由别家出牌触发，对策略外生，

### 4.3 结论（**推翻本报告 v1 的建议**）

- 把副露抬到前排水平（1.2–1.34）**已被实测过，棋子不动** → 「副露/轮」与得分的跨玩家相关
  （+0.491）**是技术的混杂，不是可拉动的因果杆**。同样的混杂适用于 `庄占比`（+0.914）。
- 因此 `speedc122`（门控放宽）**不应上线**：它只是把副露推高，而这条路已被证伪。

- 教训（方法学）：跨玩家相关 ≠ 杠杆。本项目 88 轮的多数「否证」其实也是这个形状——
  候选差异量级（+3~+16/房）低于真机可判线，所以既证不实也证不伪。

## 6. ★ 找到了 43% 停机时间的根因并修复（可确定的失分）

`var/replays/auto_*` 创建时间与 `auto_ranking.jsonl` 一致显示：

| 项 | 数值 |
|---|---|
| 观察跨度 | 147.9 小时（09-09 10:55 → 09-15 14:51） |
| 房间起始间隔中位数 | 15.0 分钟 → 平台上限 ≈ 4.3 房/小时 |
| **批次间隙 >20 分钟的累计空转** | **63.8 小时 = 跨度的 43%** |
| **折算损失房数** | **≈ 274 房** |

最大停机：**28.8 h**（09-12 18:11→09-13 23:00）、13.0 h、11.0 h、4.2 h。

**根因（代码级确认）**：`var/_watchdog.py` 的动作分支在
**match_super 与 run_bot「双缺」**时落进 `else: 暂不动作（可能在长局中）`——
即「监督器和它管的对局都不在了」反而什么都不做；唯一兜底 `ensure_keeper()` 只在
*keeper 进程不存在*时才动作，而卡死但存活的 keeper 会让它成为 no-op。
logs 佐证：09-14 10:0x 连续多次 `诊断：… run_bot=0` + `暂不动作（可能在长局中）`。

**修复**：抽出纯函数 `decide_action()`，新增 `restart_kpr` 分支——双缺**连续 5 次（7.5 分钟）**
即判 keeper 卡死、杀掉交自愈重拉；进程一旦回来计数归零（避免正常批次间隙误杀）。
单测 `tests/test_watchdog_decide.py`（5 项，含该路径回归）。**已部署**（新 watchdog pid 61804）。

> 价值：这是**不依赖策略**的确定性收益。274 房按 speedtugc 的 +17.2/房 ≈ **+4,700 分**；
> 即便按 0/房，也把排名从「被停机拖住」变成「与实际棋力相称」。

### 9.6 ★ 为什么 88 轮迭代什么都没长出来：可判别性的量级错配

真机房级 SD ≈ 146，双侧 80% 功效 / α=0.05，所需样本（每臂）：

| 可检出效应 | 房/臂 | 按 4.3 房/h |
|---|---|---|
| +10/房 | 3,343 | 777 h（32 天） |
| +20/房 | 836 | 194 h（8 天） |
| +30/房 | 372 | 86 h |
| **+50/房** | **134** | **31 h** |
| **+100/房** | **34** | **8 h** |
| +150/房 | 15 | 3.5 h |

而本项目 sim 评估出来的候选差异量级是 **+3 ~ +16/房** → 需要 **1,306 ~ 37,138 房/臂**（13 ~ 360 天）。
**这些数字从第一天起就不可能被真机证伪或证实。**

**结论（本项目最重要的一条方法学结论）**：
- 与前列的差距是 **+100 ~ +370/房**；而过去所有工作在追 **±3~16/房**——**差了 10-100 倍**。
- 因此**只有预期 ≥ +50/房 的改动值得上真机**（对应 +2pp 胜率 / +8pp 爆头率 / +0.5 fan/胡）；
  ≥+100/房 的改动 8 小时就能判定。
- 反过来说：**「精调」在这个赛制里没有意义**——它既不可判，也不足以补上差距。要追的是**结构性**变化。

**目前唯一被量化到该量级的缺口**：
- 胜率 24.2% → 30%（**≈ +100/房**，34 房/臂可判）；
- fan/胡 1.29 → 1.50（主要是爆头 23% → 34%，**≈ +50/房**，134 房/臂可判）。

副露门控 / 自杠 / 延迟 / 爆头副露机会 都**远小于**这个量级 → 已按此标准全部排除。

于是回退要等这一批（4 房 ≈ 1h）跑完才生效。

补上收尾逻辑 `kill_match_super_if_idle(expected=FALLBACK)`：

| 情形 | 行为 |
|---|---|
| `run_bot` 存活（正在打） | **不动手**（绝不中途杀对局），等本房自然结束后的下一次 90s 巡检 |
| `match_super` 存活且空闲、**仍跑旧策略** | 杀掉 → keeper 立刻用回退策略开新批次 |
| `match_super` 已跑回退策略 | 什么都不做（不重复动作、不 churn） |

关键细节：`main()` 里「策略文件已是回退目标就 early-return」会让**下一次巡检漏掉收尾**，
因此改成——`cur != FALLBACK` 才写文件+杀 keeper，但**无论是否刚回退**都继续调用
`kill_match_super_if_idle(expected=FALLBACK)`。单测覆盖了这条回归路径。

另：**批次大小保持 `rooms=4` 是刻意的**。实测批次切换空档中位仅 **0.7 min**（约 1% 吞吐），
而 `rooms=12` 会让熔断/切换的生效延迟变成最多 3h——用 1% 吞吐换 3 倍保护延迟不划算。

## 17. ★ 30 分钟房间上限 ⇒ 搜索是「有预算的」：sim 看不见这个代价

| 项 | 值 |
|---|---|
| 单房时长 | min 4.8 / **p50 15.2** / p90 18.8 / **max 24.3 分钟** |

**含义**：房间在 30 分钟处封顶（`timeout_min=30`，10 局×8 巡）。轮次是**跟着最慢玩家**推进的，
所以我们每加一点决策延迟，就直接拉长房间时长；**一旦撞上 30 分钟上限，就会少打局数 = 少拿分。**

**这条约束直接框住了搜索路线的设计**：
- 既有 rollout 原型约 **0.9s/次**决策，且它在 **83%** 的弃牌决策上启用（469/568）。

  （当前 max 已是 24.3）。
- ⇒ 搜索**必须选择性启用**（经验上 ≤ ~25% 的摸牌决策），不能像原型那样几乎每次都跑。

**而 sim 完全看不到这笔账**：`mahjong/sim.py` 没有墙钟上限，跑得越慢只是更耗时，
不会因为「撞上 30 分钟」而少打局数。这是 §13「sim 不能预测真机」的又一个结构性原因
（不只是对手池问题，而是**约束本身不同**）。

## 18. C130：把「唯一没测过的那件事」实现出来（跨向听权衡）

### 18.1 为什么它和以前所有尝试都不同

现行弃牌主键是 `(向听数, …)` —— **向听数是硬主键，永不跨级比较**。翻遍 queue：

- C038 测的是「**同一向听内**换成 ukeire」；
- C039 测的是「**同一向听内**换 tie-break」；
- C080 测的是「把早巡也交给模型」（仍受向听主键约束）。

**「1 向听只剩 2 张进张」对「2 向听有 20 张进张」谁先胡 —— 从来没有被比过。**
只有把两条路真的跑到胡才分得清，这正是 rollout 相比解析代理唯一不可替代的地方。

### 18.2 实现（`bot/speedc130.py`，基座 = SpeedTUGC，真机证据最好那一档）

按报告 §11/§13/§17 的四条硬约束：

| 约束 | 实现 |
|---|---|
| 目标 = **E[番 × 1{胡}]**（不是 P(听牌)） | 每步 `is_win` → 用 `mahjong.fan.calc` 取番（含爆头×2、4白、链），期望 = Σ番/R |
| 状态含**副露与爆头潜力** | rollout 内保留 `exposed/gangs`，胡时按真实副露数算番 |
| **副露机会建模**（C033 的致命缺陷） | 每步以 `meld_p` 概率允许手中对子「被别家打出」而碰 |
| **有延迟预算** | 仅在 向听∈{1,2} 且候选≥2 时启用；R/k/候选数可调 |

## 19. C130 的两处关键修正：公共随机数（CRN）—— 更准 **且** 更快 2.7 倍

### 19.1 问题：C032 的失败原因之一是「argmax 在噪声上」

原实现里**每个候选弃牌各自独立抽样**：A 和 B 看到的牌不同，比较的是采样噪声而不是策略差异。
这正是历史记录里 C032「R=6 → argmax 基本在选噪声」的机制。

**修法 = 公共随机数（CRN）**：一次决策内先抽好 R 条序列（长度 k，不放回）+ R×k 个副露骰子，
**所有候选复用同一批序列**。候选自己的池 = 基础池 − 自己弃的那张，遇到就跳过（继续消费序列），
保证各候选消费的是高度相关的随机性。

### 19.2 实测：噪声降一半，速度反而快 2.7 倍

`var/_c130_noise.py`：40 个真实局面，同一局面用两个不同随机种子各跑一次，看 argmax 是否一致。

| 方案 | argmax 一致率 | 40 局面耗时 |
|---|---|---|
| 每候选独立抽样（旧） | **80.0%**（32/40） | 49s |
| **CRN（新）** | **95.0%**（38/40） | **18s** |

**CRN 又快又准**——因为序列只生成一次而不是每个候选生成一次。
⇒ **单次决策成本 0.6s → 0.22s**（实测 2.7×）。

### 19.3 这直接改写了上一轮的 go/no-go 算术

| 项 | 上一轮（无 CRN） | **本轮（CRN）** |
|---|---|---|
| 单次决策成本 | ~0.6s | **~0.22s** |
| 每巡折算 | +5.4s | **≈ +1.6s** |
| 每房时长 | 15.2 → ~22 min | **15.2 → ~17.4 min** |
| **吞吐代价** | ≈ **−30%** | **≈ −15%** |
| **打平所需增益** | **> ≈ +8/房** | **> ≈ +2.5/房** |

⇒ C130 从「必须多赚 8 块才回本」变成「多赚 2.5 块就回本」——**风险收益比显著改善**。

## 20. ★ 离线反事实筛子（用**真实牌序**）——并据此否掉 C130

### 20.1 工具：`tools/discard_counterfactual.py`（本项目第一个零成本筛子）

dec 记录里每次「摸牌决策」都带 `d` = 我们**真实摸到的那张牌**。把一局内我方的真实后续摸牌序列取出来，
就能对同一局面做反事实：

- **候选线**：按候选策略选的首弃走，之后用固定续策跟完**同一批真实摸牌**；
- **基线线**：按基线策略的首弃走，同样跟完。

对比「第几张摸牌胡 / 到听牌」。**比 sim 强**：牌序是真的（sim 的牌序是自造的、还缺 30 分钟约束与真对手）。
**局限**：两条线都不吃碰、忽略对手 ⇒ 只测「首弃这一步的隐藏手速度」，**只能筛掉**明显不占优的候选。

用法：`python -X utf8 tools/discard_counterfactual.py <文件数> <基线> <候选>`

### 20.2 结论：C130 **被否掉**

70 个 dec 文件（1,907 个决策点，其中 **480 个与 tugc 分歧**）：

| 线 | 胡 | 到听 |
|---|---|---|
| C130（候选） | 308 (64.2%) | 401 (83.5%) |
| tugc（基线） | 306 (63.8%) | 401 (83.5%) |

**谁先胡：候选独占 7 / 基线独占 5**（符号检验 p≈0.77）——**基本是平局**。

⚠️ 注意样本量的教训：只看 20 个文件时是「候选独占 2 / 基线独占 0」，看起来是正收益；
扩到 70 个文件（480 分歧）就回归成 7:5。**这正是本项目反复踩的坑：小样本看起来有效。**

**判定**：C130 在它自己设计的那个维度（隐藏手速度）上**没有优势**，而它要付 **−15% 吞吐**的代价
⇒ **净亏，不上线、也不做真机 A/B**。本次否证**零成本**（没花一分榜单分）。

### 20.3 这条流程本身就是本轮最有价值的产出

本会话早先的结论是「没有便宜的可信评测」（§5.2/§13）。现在补上了一块：
**弃牌类候选可以先在这个筛子上零成本地过一遍**，只有通过者才值得花真机分数。

## 21. ★ 筛子也**不能**预测真机（r = −0.42）—— 两个便宜评测都失败

§20 用筛子否掉了 C130。本轮做了一件必须做的事：**用「已知真机结果」验证筛子本身**。
`var/_screen_validate.py`：对 6 个有真机净胜数据的策略逐个过筛（60 文件 / 1,465 决策点）。

| speedc073w2 | 250 | 8 | 6 | +0.0080 | +7.7 |
| speedc073w4 | 252 | 8 | 6 | +0.0079 | −10.0 |

### 21.1 三条必须写下来的限制

1. **筛子看不见「窗口类」改动**：`speedtug` / `speedtu` 与 tugc 的**弃牌完全相同**（只差碰/吃门控），

2. **筛子在真机最差的候选上给了最高分**（lo0 +0.0083 vs 真机 −60/房）——与 sim 一模一样的反转。
3. ⇒ **§20 对 C130 的否证不成立**：我用的是不预测真机的指标。C130 应退回「未验证」，
   而不是「已否证」。（这条自我更正很重要：否则我会用错误的理由锁死一个其实未知的候选。）

### 21.2 统一结论（本会话最重要的判断）

| 评测手段 | 成本 | 能否预测真机 |
|---|---|---|
| `mahjong/sim` 配对均值 | 低 | ❌ r = **−0.21**（§13） |
| 离线反事实（真实牌序） | 零 | ❌ r = **−0.42**（本节） |
| 监督学习 / rollout 代理（史） | 中-高 | ❌ 四次全负 |
| **真机净胜/房** | **高（≥134 房/臂才可判 +50/房）** | ✅ 唯一有效 |

**⇒ 在这个游戏里、在这个水平上，没有任何便宜的代理能预测真机。唯一可信的信号是真机房。**
这解释了这个项目 88 轮为什么在原地：**每一轮用的都是不预测的尺子。**

**⇒ 由这条推出的唯一可行工作流是「并发交替的真机 A/B」**（不是"先筛后测"）：
两个策略**交替排批**、同处一个对手池/时段，才能把 ±180/房 的日间漂移抵消掉；
顺序比较（先跑 A 一天再跑 B 一天）在这个漂移量级下没有意义。

## 22. 并发交替真机 A/B 工作台（`.ab_mode`）—— 由 §21 直接推出的唯一可行工作流

既然两个便宜评测都不预测真机（sim r=−0.21、离线反事实 r=−0.42），而日间漂移可达 ±180/房，
**顺序比较必然无效**。唯一可行的是**交替排批、同池同时段**。

### 22.1 组成

| 文件 | 作用 |
|---|---|
| `var/_ab_driver.py` | 替代 keeper 排批：每批用 A/B 交替的策略起 `match_super`；单批空档才启动（不撞 E002）；写 `var/_ab_log.jsonl` |
| `tools/ab_ctl.py` | `start <A> <B> [rooms]` / `status` / `stop`：写/删哨兵、停/起 keeper、拉起驱动 |
| `tools/ab_readout.py` | 按臂给 **净胜/房 ±95% / 正分率 / 均名次** + t 检验 + 功率提示 |
| `var/_ab_state.json` | 下一臂 + 各臂已排批数 |

### 22.2 安全设计（与 `.official_mode` 同一模式，已单测）

1. **绝不并发**：只在「无 match_super 且无 run_bot」连续确认两次后才排下一批 → 不撞 E002；
2. **启动前杀 keeper**：keeper 也会起 match_super，双开会撞 E002；
3. **watchdog 在 A/B 模式下既不自愈 keeper 也不杀任何进程**（否则会起 keeper → 双开）；
4. **`_ensure_all`（计划任务）在 A/B 模式下不拉 keeper**；
5. **`.official_mode` 优先级更高**：官方赛一开，A/B 驱动自行退出；
6. `ab_ctl stop` → 删哨兵 → 驱动自行退出 → watchdog ≤90s 把 keeper 拉回。

单测 `tests/test_ab_mode.py`（5 项）：哨兵识别、**真实哨兵绝不被测试触碰**、
读数器按臂过滤与净胜计算、`ab_ctl` 拒绝未注册策略且不落哨兵。

### 22.3 rooms 取 1 还是 4？

交替粒度 = 漂移控制强度。`rooms=1` ⇒ **每房轮换**，两臂几乎完全同池同时段（最强控制），
代价是每房多一次排批空档（实测中位 0.7 min ≈ 5% 吞吐）。建议 A/B 期间取 `rooms=1`。

### 22.4 用法（赛后用）

```powershell
python -X utf8 tools/ab_ctl.py start speedtugc speedc130 1   # 交替排批
python -X utf8 tools/ab_readout.py                            # 随时看两臂
python -X utf8 tools/ab_ctl.py stop                           # 收工，恢复 keeper
```

判定：`ab_readout` 给出 b−a 的 t 值；判 ±50/房 需 **~134 房/臂**（rooms=1 时约 3 天）。

### 22.5 与既有 `_keeper_ab.py` 的关系（重要：这不是重复造轮子，是补上它缺的那一环）

本项目**早在 09-11 就做过交替 A/B**（`var/_keeper_ab.py`，配置 `_ab_strats.json`，状态 `_ab_state.json`，

### 22.7 A/B 模式的**安全缺口**与补法（本轮发现）

**缺口**：`.ab_mode` 让 watchdog 直接 `continue` —— 于是 **`rate_guard` 在 A/B 期间完全不跑**。
如果候选臂崩坏，没有任何东西会拦它（而 guard 的回退机制在这里也无效：驱动用的是自己的配置，
不看 `_keeper_strategy.txt`）。

**补法**：把兜底搬进驱动自身 —— 排候选臂（b）之前先看该臂**自 A/B 开始以来**的净胜：

| 参数 | 值 | 含义 |
|---|---|---|
| `GUARD_MIN_ROOMS` | 4 | 样本不足不判（避免刚开 A/B 就误杀） |
| `GUARD_NET` | −150/房 | 候选臂低于此值 → **删哨兵、回退基线 a、退出** |

单测 3 项（崩坏终止 / 正常不终止 / 样本不足不终止）。全量 **238 项通过**。

### 22.8 顺手否掉的两个假设（均为零成本）

1. **"某些时段该避让"**：按小时切分 333 房 → 每格仅 3-22 房、SE 70-380/房，
   所有看似大的偏差（19 点 −116、2 点 +111、10 点 +106）都在噪声内。**无可执行结论。**
2. **用本地录制（`auto_*/**.jsonl`）做局级分解**：本地录制**只覆盖约 60%**（12 房只有 573 局 ≈ 47.75/房，
   而标准是 80/房），且**不含座位→user_id 映射** ⇒ 无法切出我方口径。**改用门户完整复盘才有意义。**

## 23. ★ 正式赛自身的监管缺口（本轮发现并修复）

## 28. ★ 战役切换：改为 **3 臂轮转** `speedtugc` / `speedc130` / `speedc073w4`

### 28.1 为什么在剩余时间里"宽度优于深度"

A/B 必须在正式赛前停（操作单 §1c），所以本战役只有约 **45 小时 ≈ 90 房**可用。这个预算下：

| 方案 | 每臂样本 | 能判定什么 |
|---|---|---|
| 2 臂（tugc vs c130） | ~45 | 只能判**大效应**（±80/房 级） |
| **3 臂（+w4）** | ~30 | 每臂更少，但**同时给三个候选排序** |

### 28.5 给两个关键守护进程加「不许死」外壳

**动机**：本会话已经四次遇到"某个自愈角色自己死了、而没人管它"（keeper / A/B 排批权 /
official keepalive / A/B 驱动）。其中 `_watchdog.py` 与 `_ab_driver.py` 都是**无限循环**——
循环里任何一次未预期异常都会让进程直接消失。

**修法**：给两者的 `__main__` 加外壳——捕获异常 → 写日志（含 traceback 末段）→ 5 秒后重启循环：

```python
def _supervised_main():
    while True:
        try:
            return main()
        except KeyboardInterrupt:
            return
        except Exception:
            log("!! watchdog 主循环异常退出，5s 后重启：\n%s" % traceback.format_exc()[-800:])
            time.sleep(5)
```

**已安全重部署**（并刻意避开上一轮那个"按 cmdline 杀掉自己 shell"的坑，改用**精确 basename 匹配 + 排除自身进程**）：
